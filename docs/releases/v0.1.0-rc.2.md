# SCRAP v0.1.0-rc.2 — release notes

**Status: DRAFT — not yet merged into `main`, adjudicated, or tagged.** This document describes
[PR #34](https://github.com/platta/scrap/pull/34) (`port-sudo-E-fix-to-main`), currently open. Per
[`docs/decisions/0015-versioning-and-release-process.md`](../decisions/0015-versioning-and-release-process.md),
a tag is created only after independent adjudication of a specific `main` commit SHA — nothing
below is final until that happens. This draft exists so that adjudication, and the decision of
whether this warrants a tag at all, can be made from a complete write-up rather than from the PR
diff alone.

**This is a defect-fix candidate, not a new-capability candidate.** Nothing about what
`v0.1.0-rc.1` proves, doesn't yet prove, or defers has changed — see
[`v0.1.0-rc.1.md`](v0.1.0-rc.1.md) for that full evidence boundary, which this release carries
forward unchanged. Read that document first; this one only describes what's different.

## Why this exists

The nightly DR (disaster-recovery) workflow started failing on 2026-10-28: GitHub's `ubuntu-latest`
runner label began migrating to Ubuntu 26.04, whose `sudo` policy silently ignores `-E`
(environment preservation) — every bootstrap/test script relied on exactly that to carry
`SCRAP_ESCROW_CONFIRMED` (and, for Topology B, other variables) across the privilege boundary.

That fix ([PR #33](https://github.com/platta/scrap/pull/33)) correctly landed on `develop` per
`docs/decisions/0016-post-rc-branching-policy.md` ("ordinary work targets `develop`"). But GitHub
Actions' `schedule` trigger always runs against the repository's **default branch** (`main`),
never whichever branch a fix merges into — so the nightly workflow kept failing every night after
the merge, on the exact same pre-fix commit, because `main` had never received it. Validating that
fix also surfaced a second, unrelated, genuinely host-affecting defect in
`bootstrap/host/install-nut.sh` (below) — not a CI-environment quirk, a real installer bug.
Together, these are judged material enough to `bootstrap/host/install-nut.sh` — real, operator-run
product tooling, not test harness — to warrant a proper tagged hotfix rather than a silent `main`
merge.

## What's fixed

### UPS capability, host installer (`bootstrap/host/install-nut.sh`, `docs/decisions/0013`)

- **Install-time deadlock.** The `nut` package's own postinst starts
  `nut-driver-enumerator.service` immediately, before this script has written `/etc/nut/ups.conf`.
  That service's own script loops calling `systemctl restart nut-server`, which fails instantly
  with no UPS configured — until systemd's restart-rate-limit trips ("Start request repeated too
  quickly"), at which point the enumerator's in-flight restart call and `nut-server.service`'s own
  ordering-queued start (`nut-server.service` → `nut-driver.target` → `nut-driver-enumerator.service`)
  deadlock each other, with nothing left to break the cycle. Root-caused live with a dedicated
  diagnostic CI run (`ps` showing the exact stuck process tree and the `deb-systemd-invoke` call
  that triggered it), not inferred from symptoms. Reproduced 2/2 times before the fix; passed on
  every run after. This is a real defect in the installer's own ordering — install the package,
  *then* write its config — not an artifact of CI's environment, even though CI is where it
  surfaced (this workflow hadn't run since September).
- **Host policy preservation.** The fix installs a temporary `policy-rc.d` (the standard
  Debian/Ubuntu mechanism to suppress a package-triggered service start) for the duration of the
  `apt-get install nut` step only. Previously, an earlier draft of this fix unconditionally
  overwrote and deleted any `policy-rc.d` the host already had; it now moves an existing one aside
  and restores it afterward, and the whole thing is under an `EXIT` trap so an interrupted run
  (Ctrl-C, or any failure mid-install) can no longer leave a stray `exit 101` policy behind
  permanently.
- **Accurate failure diagnosis.** A genuine `apt-get`/dpkg failure now says so (`"failed (exit
  $status) -- see apt's own output above"`) instead of always blaming "a stalled mirror or
  network issue," which previously was only correct for the specific `timeout`-triggered (exit
  124) case.

### Documentation

- The installer command shown in `v0.1.0-rc.1`'s own release notes, `docs/getting-started.md`,
  `bootstrap/README.md`, and the Topology B generator's own generated operator README all used
  either `sudo VAR=value sh bootstrap/install.sh` or `sudo -E sh bootstrap/install.sh`. Both depend
  on a sudoers `SETENV` policy that, when absent, drops the variable with no error an operator
  would notice as a problem — the same class of failure the CI breakage above made visible, just
  not CI-specific. Standardized everywhere on `sudo env VAR=value sh bootstrap/install.sh`, which
  is an ordinary command and doesn't depend on that sudoers policy at all.

### Internal — CI/test-harness only, no effect on an installed SCRAP instance

- Every acceptance-profile test script's `bootstrap/install.sh` invocation under `sudo`, and the
  on-failure `KUBECONFIG`-via-`sudo -E` diagnostics in all ten acceptance workflows, had the same
  `sudo -E` dependency as the nightly DR workflow. Fixed the same way: pass needed variables
  directly to `env` instead of relying on `sudo`'s own environment-preservation policy. The
  diagnostics fix means a future on-failure debug dump will actually show real cluster state
  instead of "connection refused."

## Known, separate issue — not fixed by this candidate

Validating this PR's own check suite surfaced a **second, unrelated, pre-existing defect on
`main`**: `T-A-offsite-backup` fails with `/usr/local/bin/minio: 3: Syntax error: "(" unexpected` —
the signature of `tests/profiles/t-a-offsite-backup.sh` downloading something other than a valid
binary from `https://dl.min.io/...`. This is the same class of failure `PLAT-269` fixed on
`develop` (PR #31, 2026-09-18: build MinIO server/client from pinned source instead of downloading
from `dl.min.io`) — that fix is not an ancestor of `main`, for the identical branch-targeting
reason this whole candidate exists to fix. Confirmed to affect only `tests/profiles/` (CI-only
convenience for simulating an S3 endpoint); no capability manifest or operator-facing script
depends on `dl.min.io`, so this has no footprint on an installed SCRAP instance. Left out of this
candidate's scope deliberately — it's unrelated to the `sudo -E`/`install-nut.sh` work this PR
set out to port, and deserves its own decision rather than being folded in silently.

## Getting this release

Not yet available — no tag exists. Once tagged:

```sh
git clone https://github.com/platta/scrap.git
cd scrap
git checkout v0.1.0-rc.2
```

Installation steps are otherwise identical to [`v0.1.0-rc.1`](v0.1.0-rc.1.md#getting-this-release),
using the corrected command:

```sh
sudo env CLUSTER_PATH=./clusters/<your-instance-name> sh bootstrap/install.sh
```
