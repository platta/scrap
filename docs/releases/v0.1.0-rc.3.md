## Why this exists

Investigating an intermittent `T-A-dyndns` CI failure (4 of 5 runs failing when bundled in the
ten-workflow concurrent burst a push to `main`/a PR triggers, 1 of 1 clean in isolation — a real,
reproducible pattern) found a genuine, latent defect in shipped product code, not a CI-only or
test-design issue: Alpine's `bind-tools` `nsupdate` intermittently SIGSEGVs during its own
shutdown cleanup, a known class of bug in BIND's own utilities. The crash is mostly cosmetic (it
happens after the tool has already produced valid output, on both passing and failing runs), but
it was fatal specifically for the `nsupdate` call in `capabilities/dyndns/cronjob.yaml`'s shipped
CronJob script — unlike the surrounding `dig` calls, that call isn't piped, so under `set -eu` a
crash there aborted the whole script before the script's own already-existing confirmation query
ever ran, even on runs where the real DNS update had already succeeded. Any real operator's
`scrap-dyndns` CronJob is exposed to the same crash on a genuine IP change, which is why this
warranted a proper tagged hotfix rather than a silent `main` merge.

## What's fixed

### Dynamic DNS capability, CronJob (`capabilities/dyndns/cronjob.yaml`)

- **False-failure on a successfully-applied update.** `nsupdate`'s own crash (SIGSEGV during
  `isc_app_ctxshutdown()`, triggered by a self-`kill()` call unexpectedly returning `EPERM`)
  aborted the script under `set -eu` before it ever reached the independent `CONFIRMED_IP`
  verification query the script already performs. Fixed by capturing `nsupdate`'s exit status
  explicitly instead of letting `set -e` act on it directly — the script's own existing comment
  already documented the intent ("nsupdate is not reliably non-zero on every failure mode ...
  this job re-queries the nameserver itself rather than trusting nsupdate's own exit code
  alone"); the bug was that a crash could skip reaching that re-query at all, not that the design
  was wrong.
- Root-caused live with a dedicated diagnostic CI run that dumped the dyndns Jobs list and
  CronJob schedule state at each checkpoint — not inferred from symptoms alone. That diagnostic
  first ruled out an initial hypothesis (the CronJob's own `*/10 * * * *` schedule racing the
  test's on-demand Jobs, uncoordinated by `concurrencyPolicy: Forbid`, which only governs
  scheduled-vs-scheduled runs): no extra Job ever appeared in the dump. The actual crash
  signature (`Segmentation fault (core dumped)`, `app.c:306:isc_app_ctxshutdown(): fatal error:
  kill: Permission denied (13)`) appeared identically in both a passing and a failing job's log
  in the same diagnostic run, confirming it's mostly cosmetic and narrowing the real defect to
  specifically the unpiped `nsupdate` invocation.
- Verified behaviorally before landing: a standalone simulation of the *old* pattern aborts
  (exit 139) on a simulated `nsupdate` crash before reaching the confirmation check; the same
  simulation against the *new* pattern reaches it and exits 0.

## Getting this release

`v0.1.0-rc.3` is tagged and published as a
[GitHub pre-release](https://github.com/platta/scrap/releases/tag/v0.1.0-rc.3). To install exactly
this candidate:

```sh
git clone https://github.com/platta/scrap.git
cd scrap
git checkout v0.1.0-rc.3
```

Installation steps are otherwise identical to
[`v0.1.0-rc.1`](v0.1.0-rc.1.md#getting-this-release):

```sh
sudo env CLUSTER_PATH=./clusters/<your-instance-name> sh bootstrap/install.sh
```

Read [`v0.1.0-rc.1`](v0.1.0-rc.1.md)'s own evidence boundary before relying on this candidate —
nothing about what it proves, doesn't yet prove, or defers has changed; this release is a
defect-fix on top of it, not a new evaluation of the product surface.
