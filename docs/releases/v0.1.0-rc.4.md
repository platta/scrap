## Why this exists

`authentik-postgresql-0` crash-looped reproducibly with `FATAL: could not signal for checkpoint:
Permission denied` — a self/sibling-process `kill()` call (Postgres's checkpointer signalling its
own startup process at the end of crash recovery) returning `EPERM`. Each restart re-entered WAL
recovery, hit the same denial, died again — a self-reinforcing loop with no self-resolution. Any
real operator installing or restarting Authentik's bundled Postgres on an affected host is exposed
to the same crash, which is why this warranted a proper tagged hotfix rather than a silent `main`
merge.

An earlier, narrower workaround (`seccompProfile: Unconfined` on the postgres pod/container) was
developed and merged to `develop` mid-investigation, but **it never reached a tagged release** —
during follow-up heavy-load testing it turned out to substantially reduce (not eliminate) light-load
failures while doing nothing at all under heavy load (2/2 failures either way). That gap is what
led to the real root-cause investigation below; the workaround itself was removed before this
candidate and never shipped in any tag.

## Root cause

Confirmed live, with direct process-level evidence, not inferred from symptoms alone: Ubuntu 26.04
defaults `kernel.apparmor_restrict_unprivileged_unconfined=1`. Under that setting, when a
container's AppArmor profile resolves to "unconfined", `runc` stacks it under containerd's own
default profile instead of leaving it genuinely unconfined — the container's processes carry the
label `cri-containerd.apparmor.d//&unconfined` rather than plain `cri-containerd.apparmor.d`. That
default profile only grants signal/ptrace between processes carrying the exact literal parent
label; it has no rule for two processes both stacked under `//&unconfined`, so a container process
signalling its own sibling (exactly this checkpointer/startup-process pair) gets `kill()` ->
`EPERM`, regardless of seccomp. Tracked upstream at
[containerd/containerd#14485](https://github.com/containerd/containerd/issues/14485) (fix merged
there as [PR #14487](https://github.com/containerd/containerd/pull/14487), not yet in the
containerd version the pinned k3s version ships).

A live diagnostic watcher (polling the postgres process's own `/proc/<pid>/status`,
`/proc/<pid>/attr/current`, and cgroup `cpu.stat`/`memory.events` every 2 seconds across a full
test run) directly confirmed, across 1,100 snapshots including the two immediately straddling an
observed crash, that seccomp was fully disabled and cgroup CPU-throttling/memory-pressure counters
were all zero throughout — ruling out seccomp and resource contention as the heavy-load cause
before the AppArmor-stacking mechanism was found via the exact error text matching multiple,
independently-reported real-world projects hitting the identical bug on the identical Ubuntu
26.04 migration timeframe.

Almost certainly the same underlying mechanism behind the `v0.1.0-rc.3` dyndns `nsupdate`/`dig`
false-failure fix (a self-`kill()` call returning `EPERM` during shutdown cleanup) — not reverted
here, since that fix is independently good defensive practice regardless of this root-cause fix.

## What's fixed

### Identity capability, `authentik-postgresql`'s host environment

- **`bootstrap/host/install-k3s.sh`:** disables `kernel.apparmor_restrict_unprivileged_unconfined`
  at the host level, via a persistent `sysctl.d` drop-in. Fixes the underlying AppArmor-stacking
  bug for *every* container on the node, not one chart's `securityContext` at a time — the
  correct scope for what is fundamentally a host/container-runtime default, not anything specific
  to Postgres or this chart.
- **`capabilities/identity/helmrelease.yaml`:** removes the superseded `seccompProfile: Unconfined`
  workaround (never tagged — see above). It was never the actual fix and unnecessarily weakened
  sandboxing for a security-sensitive (identity/SSO) workload; chart defaults (`RuntimeDefault`)
  apply again for both pod- and container-level `seccompProfile`.

## CI evidence

Confirmed with real controls under both load conditions this investigation distinguished
throughout — not assumed from one batch of runs:

- **Light load** (an isolated `T-B` `workflow_dispatch` run, confirmed nothing else running
  concurrently), with the sysctl fix applied and the seccomp workaround fully reverted: 1/1 clean
  pass, with the live watcher directly confirming the AppArmor label changed from the buggy
  stacked form (`cri-containerd.apparmor.d//&unconfined`) to the correct unstacked form
  (`cri-containerd.apparmor.d`).
- **Heavy load** (`T-B` run alongside the other ~9 acceptance workflows a push/PR triggers
  simultaneously — the exact condition that defeated the seccomp workaround 2/2 with zero
  exceptions): 2/2 clean passes on the same diagnostic branch, mechanistically confirmed the same
  way.
- **PR #43's own CI against `develop`** (10/10, a third heavy-load pass) and **PR #44's own CI
  against `main`** (10/10, a fourth heavy-load pass — one unrelated `apt-get` mirror timeout on
  `T-A-ups` passed cleanly on rerun) — the latter is the exact candidate (`176a373`) this tag
  points at.
- A third confidence trial on the diagnostic branch was queued but never executed, stuck for six
  days in a permanently inconsistent GitHub Actions run state; not pursued further once 4/4 clean,
  mechanistically-confirmed passes (2 of them on real PR CI, not just the diagnostic branch) was
  already a materially stronger result than anything the superseded seccomp workaround achieved.

## Getting this release

`v0.1.0-rc.4` is tagged and published as a
[GitHub pre-release](https://github.com/platta/scrap/releases/tag/v0.1.0-rc.4). To install exactly
this candidate:

```sh
git clone https://github.com/platta/scrap.git
cd scrap
git checkout v0.1.0-rc.4
```

Installation steps are otherwise identical to
[`v0.1.0-rc.1`](v0.1.0-rc.1.md#getting-this-release):

```sh
sudo env CLUSTER_PATH=./clusters/<your-instance-name> sh bootstrap/install.sh
```

Read [`v0.1.0-rc.1`](v0.1.0-rc.1.md)'s own evidence boundary before relying on this candidate —
nothing about what it proves, doesn't yet prove, or defers has changed; this release is a
defect-fix on top of it, not a new evaluation of the product surface.
